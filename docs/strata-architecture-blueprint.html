Strata

Distributed durable computing & agent execution for the JVM

Architecture · Programming model · Agent World · Delivery plan

01 / Vision and scope

Strata is a proposed JVM-native distributed entity and agent execution runtime. Stratum is its visual development and observability environment; inferra is a separate Rust inference project. The goal is to support ordinary reactive services, stateful entities and durable AI workflows in one ecosystem, without requiring every request to pay durability overhead.

Actors own state. Virtual threads execute work. Journals record execution. Shards determine placement. Netty handles traffic. Strata defines guarantees.

Inspired by Golem’s durable WASM agents, Akka/Pekko actors, Restate virtual objects and game-engine entity models. This is a design baseline, not a claim that the runtime exists or has been benchmarked.

02 / Golem inspiration and execution model

A durable agent has a stable identity, mutable logical state and recorded execution history. It can be modeled as a state transition function (next state, output) = f(state, input). Its history is not necessarily an immutable audit ledger. Golem can reconstruct execution using its operation log; Strata proposes explicit durable steps instead of arbitrary JVM stack recovery.

Invocation
Counter(alice).increment()
↓
Identity routing
Resolve entity and owner
↓
Execution
Apply command to current state
↓
Durable commit
Persist event or state and response metadata
↓
Recovery
Reconstruct state and resume eligible work

Independent identities can execute concurrently; a hot single identity may serialize mutations. For 10,000 requests/s, a hypothetical 5 ms serialized operation permits 200 operations/s per identity before overhead. This is a capacity illustration, not a benchmark. Sharded counters trade simple global ordering for parallelism.

Never block Netty event loops or Pekko dispatchers with LLM calls. Virtual threads must not mutate actor-owned state. Bound concurrency, queues and provider quotas. ZIO/Cats Effect fibers are optional future integrations; neither fibers nor Loom provide crash durability by themselves.

05 / Durability and failure semantics

Step requested
Persist invocation and stable step identity
↓
Execute effect
Use idempotency key; enforce policy and timeout
↓
Commit result
Persist result before advancing workflow
↓
Crash / restart
Recover ownership and journal; reuse committed results
↓
Continue
Retry or reconcile ambiguous effects; resume at next step
ModeGuarantee
EPHEMERALNormal request execution
STATEFULSharded volatile entity
PERSISTENTRecoverable entity state
DURABLEExplicit journaled steps, timers and signals

DurableFiber is a logical execution identity, not a serialized Java stack. Replay requires deterministic control flow, stable step IDs, recorded nondeterministic inputs and version compatibility. External effects may succeed before their result is committed; use idempotency, outbox/inbox or reconciliation. No blanket exactly-once guarantee. Fence stale owners, handle duplicate messages, test network partitions and persist timers. A suspended approval must release its physical thread.

06 / Proposed developer API

All Strata annotations and interfaces below are illustrative, not implemented or compiled.

@StrataEntity("counter")
class Counter {
    @EntityState long count;
    @EntityMethod long increment() { return ++count; }
}

@StrataAgent("research")
class ResearchAgent {
    @Durable
    Report research(String topic, DurableContext ctx) {
        var plan = ctx.step("plan", () -> createPlan(topic));
        var data = ctx.step("retrieve", () -> search(plan));
        ctx.awaitSignal("approval", Approval.class);
        return ctx.step("report", () -> synthesize(data));
    }
}
@PostMapping("/agents/{id}/research")
Mono<InvocationId> research(@PathVariable String id,
                            @RequestBody ResearchRequest req) {
    return strata.submit(ResearchAgent.class, id, req);
}

Long-running invocations should return an ID (HTTP 202) and expose status, result and streaming endpoints. Approval decisions must be checked before proceeding; the snippet is schematic.

Record decisions and tool results, not private model reasoning. Protect sensitive data with encryption, access controls, redaction and retention. Use explicit approval for consequential actions. Track token budgets and provider rate limits. Passivate idle entities; 100,000 logical identities need not mean 100,000 active threads.

08 / Agent World — strategy-game inspiration

Age of Empires provides a useful metaphor: villagers, scouts and specialized units have identities, capabilities, tasks and resources. Golem agents do not inherently possess goals or autonomy; these must be programmed.

World View should visualize actual placement and message flow; simulated failures must be labeled separately from live operations. Future brains: state machines, behavior trees, rule engines, GOAP and LLM hybrids. Compose capabilities rather than requiring deep inheritance.

10 / Stratum observability and benchmark plan

The earlier Stratum v0.2 prototype used synthetic charts and raw local CLI output; it is not a live metrics implementation. Replace synthetic metrics with instrumented runtime telemetry, preserving a clearly labeled simulation mode.

Metric groupMeasurements
HTTPThroughput, p50/p95/p99, errors, dropped load
EntitiesActive/passivated/suspended, shard distribution, hot keys
DurabilityReplay time, journal growth, recovery latency, timer drift
ResourcesCPU, heap, virtual threads, queue depth, RPC latency
AITokens, cost, tool latency, committed result reuse, duplicate effects

Compare plain WebFlux, Pekko, Strata, Restate and Golem with equivalent workloads: counter, shopping cart, research agent. Test uniform and hot-key load, crash before/after commit, node loss, duplicate requests, approval suspension and recovery. Target 10k HTTP requests/s as an experiment, not a release promise. Record hardware, versions, workload and durability settings.
